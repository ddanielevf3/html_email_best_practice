Table-based HTML

Reference guide · markup

Why email HTML is still built with <table> and inline CSS instead of the <div>/Flexbox/Grid approach used on the web — and how to apply that base to layout, typography, responsiveness, custom fonts and animated GIFs.

01The underlying problem

When building for the web, the browser is (more or less) a single, predictable environment: Chrome, Firefox, Safari and Edge share modern rendering engines (Blink, Gecko, WebKit) that fully support CSS3, Flexbox, Grid, media queries and JavaScript.

Emails don't open in a browser. They're rendered by the mail client's own rendering engine, and these engines are extremely varied:

ClientRendering engine
Outlook 2007–2019 (desktop, Windows)Microsoft Word (engine replaced since 2007)
Outlook 365 (new, Windows)WebView2 (Chromium) — not on every version
Outlook for MacWebKit
Gmail (web)Proprietary engine, aggressive HTML sanitisation
Apple Mail / iOS MailWebKit (good CSS support)
Yahoo Mail, AOLProprietary engines, partial CSS support

The critical case is Outlook desktop on Windows: since 2007, Microsoft has replaced the HTML rendering engine with Word's, for security and Office-integration reasons. Word was never designed to interpret modern CSS: it doesn't support (or only partially supports):

  • float, position: absolute/relative
  • margin (often ignored on <div>s in many versions)
  • max-width, min-width reliably
  • Flexbox and CSS Grid (not supported at all)
  • background-image via CSS (needs a VML fallback)
  • border-radius
  • display: table as a "modern" substitute for real tables

A layout built with <div> + modern CSS (the "correct" approach for a website) simply collapses or breaks in Outlook.

02Why tables work

The <table> element is one of the oldest and most stable in HTML. Every mail client, including Outlook's Word engine, interprets it in essentially the same way because:

  • Word supports tables natively (it's a word-processing document: tables are a first-class element), so rendering stays reliable even in the most restrictive client.
  • <td>/<tr> provide a predictable box model: width, alignment (align, valign), padding and borders behave consistently without relying on modern CSS properties that some clients ignore.
  • Nested tables let you recreate columns, sidebars and "bulletproof" buttons without ever using float or position.
  • They don't suffer from margin collapsing, which affects <div>s in partial-CSS environments.
  • colspan and rowspan give grid-style layout control that works everywhere, while CSS Grid isn't supported by any Word-based client or by older Gmail clients.
In short: tables aren't the "modern" choice, they're the choice that works in the client with the lowest common denominator of support, which historically is Outlook on Windows — a client still widely used in enterprise/B2B settings.

04Why inline CSS is preferable to external or head <style>

On a website, inline CSS (style="..." on a single tag) is considered bad practice: it breaks the separation between structure and presentation, is hard to maintain, and isn't cacheable. In email, the opposite is true, for very concrete reasons:

  • Many clients strip the entire <head>, and with it any <style> block inside it. Gmail (in some contexts, particularly when an email is forwarded or viewed in "conversation" mode), some enterprise webmail clients and several mobile clients sanitise incoming HTML and cut everything outside the <body>, including stylesheets linked externally with <link>.
  • External CSS almost never loads: for security and privacy reasons (avoiding tracking via HTTP requests), mail clients don't allow loading remote CSS resources. A template that relies on an external .css file arrives at the recipient completely unstyled.
  • A <style> block in the head is supported "unevenly": some clients interpret it, others strip it, others interpret only part of it (for example supporting classes but not descendant selectors or pseudo-selectors). The result isn't predictable.
  • Inline CSS, on the other hand, is supported almost universally, because every client, even the most restrictive one, still has to render the style attribute on individual tags to show any formatting at all — the same principle by which a Word document applies formatting character by character.
  • As a practical consequence, when a template is generated (e.g. by a drag-and-drop editor or an automated tool), the last step is almost always CSS inlining: an automated process that takes the rules written in a "readable" stylesheet during development and transfers them, property by property, into the style attribute of every tag in the final markup. This lets you write and maintain clean CSS during development while still shipping "ugly" but reliable HTML at send time.

In practice: external or head CSS is a development convenience, not something you can rely on in production; inline CSS is the only approach that guarantees the styling actually reaches the recipient, in every client.

05Why <h1>, <h2>, <p> aren't used the way they are on a website

On a website these tags play a dual role: semantic (document structure, SEO, accessibility) and visual (the browser automatically applies a consistent, predictable default style). In email, the second role isn't reliable:

  • Every client applies its own default style to <h1>–<h6> and <p>, and these defaults aren't uniform: font size, top/bottom margins and font weight vary from client to client. An <h1> that looks large and well-spaced in Apple Mail can appear oversized, with excessive margins or a completely different font, in Outlook or on an Android client, because each applies its own user-agent stylesheet, and some of these aren't reliably overridden by the template's CSS.
  • Default margins are one of the most common problems: many clients (particularly Outlook and some mobile clients) apply their own vertical margins that the template's CSS can't reliably neutralise (because inline margin: 0 is respected in some clients and ignored in others), causing unwanted, inconsistent spacing across clients.
  • Gmail in particular rewrites/normalises some semantic tags, compressing or altering heading styles unpredictably when it "cleans up" incoming HTML.
  • There's no SEO benefit: an email is never indexed by search engines, so the main reason a website prefers semantic <h1>/<h2> tags simply doesn't apply here.
  • The accessibility benefit only partly holds: semantic tags still help screen readers, so they shouldn't be avoided on principle — the point is not to rely on their default visual style.

The standard approach is therefore:

  1. You can keep using <h1>, <h2>, <p> for semantics (fine for accessibility), but every desired visual style must be declared explicitly and inline on each one (font-size, font-family, font-weight, line-height, margin, colour), never relying on the browser/client default.
  2. Many professional templates prefer to avoid heading/paragraph semantic markup altogether, achieving the same visual result with a table <td> containing inline-styled text (optionally with a role attribute or alt text for accessibility) — precisely to eliminate any client-"inherited" style variable and be 100% certain of the final result.
  3. Either way, margins must always be reset and explicitly re-declared (style="margin:0; padding:0;") on every heading/paragraph, to stop each client's user styles adding unwanted spacing.

In short: on a website you rely on the browser's default style for headings and paragraphs because it's consistent; in email that default isn't consistent across clients, so every visual property must be declared explicitly and inline, tag by tag, exactly like the rest of the layout.

06Font-size and line-height: getting the sizes right

Just like margins and tag styles, font-size and line-height shouldn't be left to the client's default: they must be declared explicitly, in pixels, on every text element, for the same reason outlined in the previous sections — no client guarantees a default consistent with the others.

6.1 Units: px only

  • Always use px, never em, rem or %: relative units depend on an "inherited" font-size that isn't reliable in mail clients, and some clients (Outlook in particular) interpret them inconsistently.
  • The value must always be declared inline on every text tag (style="font-size:16px; line-height:24px;"), never left to an inherited stylesheet.

6.2 Recommended sizes per element

ElementFont-sizeLine-heightRatio
Body copy14–16px20–24px~1.4–1.5×
Main heading (H1 / hero)24–32px30–38px~1.2–1.3×
Subheading (H2)20–24px26–30px~1.25–1.3×
Sub-section (H3)16–18px22–24px~1.3×
Button/CTA text16–18px (bold)= font-size or +2px~1.0–1.1×
Captions, notes, footer/legal11–13px16–18px~1.4–1.5×
Preheader (hidden in preview)12–14pxn/a (display:none)—
Never go below 13–14px for body copy (below this threshold, many mobile clients, iOS in particular, automatically enlarge the text — text size adjust — altering the intended layout) and never go below 11px even for legal/footer text, which remains the minimum readable size on screen.

6.3 How to calculate line-height

The ratio between line-height and font-size follows the same typographic logic as the web, but must always be expressed as an absolute value (px), never as a bare number or percentage:

  • Long body text (paragraphs): a ratio of 1.4×–1.6× the font-size. Example: font-size:16px → line-height:22px–24px. A line-height too tight (close to 1×) makes multi-line text tiring to read; one too loose (over 1.8×) visually breaks up the paragraph.
  • Titles and headings (few lines, large text): a tighter ratio, 1.2×–1.3×. Example: font-size:28px → line-height:34px. Headings don't need the "breathing room" required by long paragraphs.
  • Buttons/CTAs (single line): a ratio of ~1×–1.1×, i.e. line-height equal to or slightly above the font-size, to correctly centre the text inside the button without adding unwanted vertical space.

6.4 Outlook's line-height bug

Outlook (Word engine) has a well-known, problematic behaviour: when line-height is expressed as a percentage or a bare number (e.g. line-height:1.5), Word applies its own line-spacing algorithm that often adds excess spacing compared to what was declared, especially across multiple lines of text.

The standard fix is to add, in the same inline style, Microsoft's proprietary property:

HTML
<td style="font-size:16px; line-height:24px; mso-line-height-rule:exactly; margin:0;">
  Paragraph text...
</td>

mso-line-height-rule:exactly forces Outlook to respect exactly the declared px value instead of recalculating it, and is considered a rule worth adding by default to every multi-line text block in a professional email template.

6.5 A note on mobile

Unlike the web, where font-size is often reduced on small screens, in email the practice is the opposite: body text size is kept the same or slightly increased on mobile (typically via the media queries covered in the Responsive Design guide), because the screen is smaller but viewed closer up, and the primary goal remains readability, not information density.

07Custom fonts (web fonts)

Brand fonts follow the same underlying logic as the rest of this document: what works on a website isn't guaranteed in email, and an explicit fallback must always be planned for.

7.1 Support is fragmented, not binary

On the web, an @font-face loaded from Google Fonts or Adobe Fonts works identically in every modern browser. In email, web-font support is partial and inconsistent across clients:

  • Clients that support them (generally, when implemented via @font-face): Apple Mail (desktop and iOS), Outlook for Mac, and various WebKit-based clients.
  • Clients that ignore them entirely: Outlook desktop on Windows (Word engine: @font-face isn't interpreted), the Gmail app on Android and iOS, and various native Android clients. These clients automatically fall back to the next font declared in the stack, simply ignoring the custom one.
  • Some clients that do support @font-face don't load external resources (the same problem covered for stylesheets in section 04): if the font is referenced via a <link> to an external service (e.g. Google Fonts), loading can be blocked regardless of the client's technical support for @font-face.

The practical result: a meaningful share of recipients will always see the fallback font, not the brand one. This isn't a defect to "fix" with more hacks (section 09), but normal behaviour to design for from the start.

7.2 How to declare it correctly

Unlike the rest of the document's CSS, @font-face can never be written inline (there's no way to declare an @font-face inside a tag's style attribute): it must go in a <style> block in the <head>, knowing that — as covered in section 04 — that block might still be removed by some clients, which will then simply use the fallback.

HTML + CSS
<head>
  <style>
    @font-face {
      font-family: 'Brand Sans';
      src: url('https://example.com/fonts/brand-sans.woff') format('woff');
      font-weight: 400;
      font-style: normal;
    }
  </style>
</head>

Then, on every text element, always declare a font stack with a fallback, never the custom font alone:

HTML
<td style="font-family:'Brand Sans', Arial, Helvetica, sans-serif;
           font-size:16px; line-height:24px;
           mso-line-height-rule:exactly; color:#333333;">
  Message text...
</td>
  • The first name is the brand font.
  • The second and third are "web-safe" fonts installed by default on the operating system (Arial, Helvetica, Georgia, Times New Roman, Verdana, Trebuchet MS, Courier New): they're the safety net for every client that ignores @font-face or fails to load the font file.
  • The last value is a generic family (sans-serif or serif), as a final guarantee.

7.3 Don't design "by eye": verify with Litmus or Email on Acid

The problem with custom fonts is that it's not visible during development: opening the HTML file in a browser, or even in a desktop client like Apple Mail, the custom font almost always loads correctly — the developer's browser doesn't reproduce the behaviour of Outlook, the Gmail app or the other clients that ignore it. Without a dedicated test, it's easy to have the false impression that "the font works", because you're only testing on the clients that already support it.

For this reason, before finalising a template with custom fonts, use a cross-client preview tool like Litmus or Email on Acid: these services send (or render) the email across dozens of real client/device/OS combinations and return actual screenshots of how it appears in each, letting you concretely verify:

  • on which clients the brand font is actually applied;
  • whether the declared fallback (Arial, Helvetica, sans-serif, etc.) is legible and keeps an acceptable visual hierarchy even when the main font doesn't load;
  • whether sizing and line-height (section 06) stay balanced even with the fallback font, which often has different metrics (average character width, height) from the brand font and may therefore wrap at different points or take up more vertical space.

This step isn't optional if you're using custom fonts: it's the only way to know, with certainty rather than assumption, what real share of recipients will see the brand font and what share will see the fallback — since your own development environment isn't representative of the full range of clients.

08A complete practical example

A minimal but complete example — header, body copy, call-to-action button and footer — that applies every rule covered so far: nested tables, inline CSS, role="presentation", mso-line-height-rule:exactly, a "bulletproof" button and a conditional wrapper for Outlook.

HTML
<!-- Outer wrapper: gives the background colour to the whole client window -->
<table role="presentation" width="100%" cellpadding="0" cellspacing="0"
       border="0" style="background-color:#f2f2f2;">
  <tr>
    <td align="center" style="padding:24px 12px;">

      <!--[if mso]>
      <table role="presentation" width="600" cellpadding="0"
             cellspacing="0" border="0" align="center"><tr><td>
      <![endif]-->

      <!-- Main container, fixed 600px width -->
      <table role="presentation" width="600" cellpadding="0"
             cellspacing="0" border="0" align="center"
             style="width:600px; max-width:600px; background-color:#ffffff;">

        <!-- Header/title: no h1, text straight in the td -->
        <tr>
          <td align="center"
              style="padding:32px 24px 16px 24px; font-family:Arial,
              Helvetica, sans-serif; font-size:26px; line-height:32px;
              mso-line-height-rule:exactly; font-weight:bold;
              color:#1a1a1a;">
            Welcome to Acme
          </td>
        </tr>

        <!-- Body copy: no p, text straight in the td -->
        <tr>
          <td align="left"
              style="padding:0 24px 24px 24px; font-family:Arial,
              Helvetica, sans-serif; font-size:16px; line-height:24px;
              mso-line-height-rule:exactly; color:#333333;">
            Thanks for signing up. Your account is ready: you can now
            log in to the dashboard and start setting up your first
            project.
          </td>
        </tr>

        <!-- Call to action: "bulletproof" button -->
        <tr>
          <td align="center" style="padding:0 24px 32px 24px;">
            <table role="presentation" cellpadding="0" cellspacing="0"
                   border="0">
              <tr>
                <td align="center" bgcolor="#2563eb"
                    style="border-radius:4px;">
                  <a href="https://example.com/dashboard"
                     style="display:inline-block; padding:14px 28px;
                     font-family:Arial, Helvetica, sans-serif;
                     font-size:16px; line-height:16px; font-weight:bold;
                     color:#ffffff; text-decoration:none;
                     border-radius:4px;">
                    Go to dashboard
                  </a>
                </td>
              </tr>
            </table>
          </td>
        </tr>

        <!-- Footer: no p, text straight in the td -->
        <tr>
          <td align="center"
              style="padding:16px 24px; background-color:#f7f7f7;
              font-family:Arial, Helvetica, sans-serif; font-size:12px;
              line-height:18px; mso-line-height-rule:exactly;
              color:#888888;">
            Acme Inc. - 1 Roma Street, Milan -
            <a href="https://example.com/unsubscribe"
               style="color:#888888;">Unsubscribe</a>
          </td>
        </tr>

      </table>

      <!--[if mso]>
      </td></tr></table>
      <![endif]-->

    </td>
  </tr>
</table>

8.1 What each block does, line by line

  • Outer wrapper (width="100%"): the outermost table, as wide as the client window. It only exists to give the background colour (#f2f2f2) to the whole visible area, not to the actual content.
  • Conditional comment <!--[if mso]> ... <![endif]-->: visible only to Outlook. It adds an extra fixed-width table (width="600") because, unlike other clients, the Word engine doesn't always reliably respect max-width on the inner container: this wrapper "forces" the correct width only where it's needed.
  • Main table (width="600", align="center"): the actual content container, centred, with a fixed width declared both via the HTML attribute and via inline CSS (width:600px; max-width:600px;) — this double declaration (section 03) ensures the value is respected by the largest possible number of clients.
  • Header row and body-copy row: no <h1> or <p>. As noted in option 2 of section 05, the text is written straight inside the <td>, with all visual styling (font-size, line-height, colour, weight) declared inline on the cell itself. The sizes used (26px/32px for the title, 16px/24px for the body) come directly from the table in section 06, and mso-line-height-rule:exactly neutralises Outlook's bug from section 7.4.
  • CTA button: not a simple styled <a>, but a single-cell mini-table with bgcolor on the <td>: this ensures the button's coloured background is visible even in Outlook, where CSS background-color on an <a> isn't always reliable. The link text has line-height equal to the font-size (a ~1× ratio), as recommended for single-line elements.
  • Footer row: a reduced font-size (12px), consistent with the readability minimums given in section 06, and the same inline treatment as every other line of text.

This example is deliberately minimal (a single column, a single button): the same logic — nested tables, always-inline CSS, double HTML+CSS width declarations, a table-based button, mso-line-height-rule:exactly — applies identically to more complex layouts (two columns, images alongside text, a header with a logo), simply by adding further nested <table>/<td> elements inside the cells already present.

09Why you shouldn't "overkill" the code with device-specific styles

There's a recurring temptation among email developers: as soon as you discover that a client (some version of Outlook, the Gmail app on a particular Android build, Yahoo Mail, Outlook Web Access...) renders something slightly differently, you add a CSS hack targeted specifically at that client (a class like .ExternalClass, an [owa] selector, an @media block for a specific resolution, a conditional comment for a single Outlook build). Doing this once is fine; doing it systematically across dozens of client/version combinations becomes a bigger problem than the one it solves.

9.1 The number of combinations is unmanageable

Unlike the web, where there are effectively 3–4 rendering engines (Blink, Gecko, WebKit) updated constantly and predictably, email involves dozens of real combinations of client, operating system, app version and even viewing mode (webmail vs app vs desktop client) for the same service: Outlook 2016/2019/365 desktop, Outlook.com, Outlook for iOS/Android, Gmail web/iOS app/Android app, Apple Mail desktop and on every iOS version, Yahoo, Samsung Mail, Thunderbird, and others still less widespread. Chasing pixel-perfect rendering on every single one of these combinations isn't realistically achievable, and every hack added to fix one specific case is code that's almost never re-tested once it's in production.

9.2 Hacks pile up and interact unpredictably

Every CSS class or rule targeted at a specific client (.ExternalClass, [owa], u + .body, .MsoNormal, @media blocks nested for very narrow width ranges, and so on) is meant to isolate that client, but in practice these rules all coexist in the same HTML document and can overlap or conflict with each other: a hack written to fix Outlook 2016 can, combined with a second hack meant for Yahoo, produce an unwanted effect in a third client that neither author anticipated. The more hacks pile up, the harder it becomes to predict — and above all to test — every possible interaction, because cross-client testing (tools like Litmus or Email on Acid, or real devices) has a cost and rarely covers the entire matrix of combinations.

9.3 Clients change without warning, hacks don't

Unlike browsers, which communicate roadmaps and changes through public channels, mail clients (webmail like Gmail and Outlook.com in particular) update silently, with no public changelog for the email developer. A hack that fixes a rendering defect today might, after a client update, no longer be needed — or worse, start introducing the very problem it was meant to solve, because the client has since fixed its own baseline behaviour and the hack is now layered on top of already-correct rendering. Code full of very specific fixes ages badly and is hard to keep under control over time, because there's no way to know when a hack has become obsolete without manually re-testing it on that client.

9.4 The weight of the code has a real cost: Gmail's clipping

Gmail (particularly on the web interface) automatically truncates emails whose HTML exceeds roughly 102 KB, inserting a "Message clipped — view entire message" link and hiding everything after it — including, in the worst case, the footer, the unsubscribe/disclaimer link or the tracking pixel. A template with dozens of redundant hacks, duplicated @media blocks for every conceivable width and multiple conditional comments for every Outlook version reaches this limit far faster than a lean template.

9.5 The right approach: a solid base, a few well-documented, well-tested hacks

  • Table-based layout with inline CSS (sections 01–04) alone covers the vast majority of clients with no extra hacks needed.
  • The few hacks worth keeping are the ones that are standard and have been documented for years in the email community (the <!--[if mso]> conditional comments, mso-line-height-rule:exactly, the table-based bulletproof button): they're extensively tested, stable, and fix real structural problems, not marginal aesthetic details.
  • Responsive media queries should stay few and simple (typically just one, to stack columns below 600px), not multiplied for every conceivable breakpoint or device.
  • Focus on the clients that cover the majority of real end users (typically Gmail, Apple Mail/iOS, Outlook and Yahoo together cover the vast majority of opens), rather than optimising for marginal clients representing a negligible fraction of the audience.
  • Accept that the result won't be pixel-identical on every client: the goal is a message that's readable, well-structured and functional everywhere, not indistinguishable client by client.

In short: every line of CSS targeted at a specific case is a permanent cost (file weight, conflict risk, future maintenance) for an often marginal and temporary benefit. It pays to invest in the solidity of the table-based/inline-CSS foundation rather than chasing every single exception.

10Animated GIFs

Animated GIFs are one of the most common ways to add motion to an email without resorting to video or interactive code (section 01). The same general rule of this document applies here too: support isn't uniform, and a fallback must be designed for, not ignored.

10.1 Outlook doesn't animate them: it only shows the first frame

The critical case, once again, is Outlook desktop on Windows (Word engine): it doesn't play the animation, but shows the GIF's first frame statically and stops there. This isn't an isolated bug in a specific version: it's a structural, years-stable behaviour of the engine.

The practical consequence is a design rule, not a fix to apply afterwards: the GIF's first frame must work on its own as a complete static image. It must contain the main message, the product, the call to action — everything needed to communicate, not a transition frame, a "blank" frame, or one intended only to introduce the animation. Never put critical content (a price, an offer deadline, legal text, the call-to-action button) only in a frame after the first one: on Outlook, that content simply won't exist for the recipient.

The rest of the frames should be treated as an optional enhancement, following exactly the same controlled-degradation logic covered in the Responsive Design guide for media queries: whoever sees it (most clients) gets a better experience; whoever doesn't (Outlook) still receives a complete, readable message.

10.2 File weight

Animated GIFs, by their nature, weigh more than an equivalent static image (more frames = more data), and this ties directly into the overall weight problem covered in section 10.4: an email approaching the ~102 KB threshold above which Gmail applies clipping reaches that limit much faster if it contains heavy GIFs. The most common practical precautions:

  • limit the number of frames and the colour palette to the minimum needed for the desired effect;
  • compress the GIF with dedicated tools before sending;
  • avoid using GIFs for very large areas of the layout (e.g. a full-width animated background): the effect is almost never worth the weight cost.

10.3 Alt text and images blocked by default

As already noted in section 01, many clients block image loading by default, showing only the alt text in their place until the recipient chooses to "show images". This applies to GIFs too: the alt attribute isn't optional, because for a real share of recipients it'll be the only thing visible until they enable images.
