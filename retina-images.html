Retina Images

Reference guide · image assets

Why a "1:1" image looks blurry on most phones today, why exporting a file "at 2x" doesn't automatically make it sharp, and the checklist to actually get retina-ready assets into an email.

The one thing almost every designer gets wrong: "retina" does not mean "the file has more pixels." It means the picture actually contains more real detail. Those are not the same thing, and mixing them up is the single most common mistake in this whole topic.

Picture a blurry photo on your phone. If you pinch-zoom it to make it twice as big, does it get sharper? No — it just gets bigger and blurrier, because you're stretching the exact same information over more space. You haven't added anything that wasn't already there.

Exporting a design "at 2x" works exactly the same way. If the photo, icon or screenshot you placed in your design was already low-resolution, doubling the export's pixel count doesn't invent new detail — it just stretches the existing blur over a bigger file. The file gets heavier. It does not get sharper.

This is exactly the trap: "I exported my design at 600px instead of 300px, so it's retina-ready." That's only true if the things placed inside that design — the photos, the icons — were themselves already sharp enough at 600px. If a 300px stock photo was simply stretched by the software to fill a 600px frame, the exported file is technically "2x" on paper, but it looks exactly as blurry as the 300px original — it's just a bigger file of the same blur.

The other one just got stretched — and stretching a blur only ever makes a bigger blur, never a sharp picture. That's the entire concept in one sentence: the export setting doesn't create detail; it can only preserve or reveal detail that was already there. The sections below (14–18) go into the technical reasons why, and how to check before you ship.

01CSS pixels and physical pixels: two different things

When you declare width="300" or style="width:300px;" on an image, that value is not a count of physical screen pixels: it's a CSS (or "logical") pixel, an abstract unit of measurement that the operating system/browser then translates into physical pixels based on the screen's density.

The ratio between physical pixels and CSS pixels is called the Device Pixel Ratio (DPR):

Screen typeDPR1 CSS pixel maps to
Standard screen ("1x")11×1 physical pixel
Retina / high-density screen ("2x")22×2 = 4 physical pixels
Very-high-density screen ("3x", many recent Android phones and iPhones)33×3 = 9 physical pixels

Visually, this is what "1 CSS pixel" actually is on each screen type — the same single square of space, subdivided into more and more real, physical pixels as density increases:

This is exactly why a 1x image looks blurry on a 2x screen: the file only ever supplies one colour value per big square, but the screen has four physical dots to fill in that same space — so it has to invent the other three by interpolating.

A box declared 300px CSS wide therefore occupies:

  • 300 physical pixels on a 1x screen
  • 600 physical pixels on a 2x Retina screen
  • 900 physical pixels on a 3x screen

The number "300px" in the code never changes: what changes is only how many physical screen pixels are used to draw it.

02Why this matters more than ever in email

Today, most emails are opened on a smartphone (iPhone and the majority of recent Android devices), and virtually every modern smartphone has a high-density screen (2x or 3x). This means most recipients view emails on a Retina screen, not a standard one.

The practical problem: if the uploaded image file has exactly the same pixel resolution as the box it's shown in (e.g. a 300×150-pixel file shown in an <img width="300">), it will look sharp on a 1x screen — but on a 2x Retina screen, that 300×150-pixel file gets enlarged (upscaled) by the browser to fill the 600×300 physical pixels available. The browser has to "invent" the missing pixels through interpolation, and the result is a visibly blurry or pixelated image — exactly the same effect as a screenshot zoomed to 200% on a computer.

03The basic rule: export at 2x, declare the dimensions at 1x

The standard fix is simple to state: the image file must have double (or triple) the real pixels compared to the size it will be displayed at, while the HTML continues to declare the desired "logical" size (the 1x one):

HTML
<!-- The file logo@2x.png is actually 600px wide,
     but is declared at 300px: on a Retina screen the
     real 600px get "compressed" into the 300px CSS space,
     appearing sharp. On a standard screen it's simply
     scaled down, with no perceptible loss. -->
<img src="logo@2x.png" width="300" height="150"
     alt="Company logo"
     style="width:300px; height:150px; display:block;">

In practice: you export the file at a higher resolution, but you always declare the 1x display size in the width/height attributes and the inline CSS. This applies to logos, hero images, icons, image-based buttons — any visual asset in the email.

04Exporting "at 2x" isn't enough if the source design isn't retina-ready

This is where the most common mistake hides, and it's the reason many emails "exported at 2x" still look blurry on Retina screens even though the file genuinely has double the declared pixels.

4.1 Doubling the dimensions isn't the same as doubling the detail

An image file can end up with double the pixels in two completely different ways:

  • A genuine resolution doubling: the source element (a vector, a font, a geometric shape) is redrawn/recalculated from scratch at the higher resolution. Every single pixel of the 2x file is computed directly from the original geometry (vector curves, text outlines, etc.): the result contains real, additional visual information.
  • Upscaling/interpolation: the source element is already a low-resolution raster file (a photo, a screenshot, an already-compressed stock image), and the design software simply enlarges the canvas and interpolates the existing pixels to fill the extra space. The final file does have double the pixels "on paper", but it contains not a single extra bit of detail compared to the original: it's simply the same blurry image, made bigger.

The second case is exactly why an image "exported at 2x" from a design that wasn't built to be retina-ready isn't actually retina: the declared pixel count doubles, but the perceived sharpness stays that of the original low-resolution asset. The Retina screen will still display those interpolated, "invented" pixels, which remain just as blurry as the source image.

4.2 When "@2x" export genuinely works

Exporting at 2x only produces a genuinely sharp result when the elements in the design are resolution-independent from the outset:

  • Real text (not text converted to an image): fonts are vector-based by nature, so they're automatically redrawn at the correct density by any export tool.
  • Vector shapes, SVG icons, illustrations created directly in the design tool (rectangles, circles, paths, vector icon sets): these too are recalculated pixel by pixel at the requested resolution. This only applies inside the design tool, for the designer doing the export — email clients don't reliably support SVG or any vector format, so whatever you ship is always a raster image (PNG/JPG) in the end. What being vector-based buys you is a genuinely sharp raster export at any resolution you ask for, not a vector file you can actually send in the email.
  • Photos or raster images that, from the very start, were imported at a sufficiently high resolution (ideally already at 2x or 3x relative to the final display size): here, exporting "at 2x" merely exports pixels that already existed in the original photo, rather than inventing them.

4.3 The question to ask before exporting

Ask this, not "did I export at 2x?": did the source asset already have, from the start, enough real pixels to fill that resolution? If the answer is no — for example a stock photo that was already low-resolution, or a screenshot pasted into the design document — no "2x" export option in the software will recover detail that the source image never had.

4.4 If the design is already retina-ready, the export is at 1x (not 2x)

There's a point that often causes confusion: the number "2x" doesn't have to appear as a multiplier in the export panel. There are two equally valid ways to end up with a genuinely retina file:

  • You design at the logical size (1x) and use the tool's "@2x" export option (Figma, Sketch, Photoshop, etc.), which doubles the pixels at export time. This only works, as covered in 4.1–4.2, if the elements involved are vector-based or the raster assets were already high-resolution.
  • You design the entire artboard/canvas already at the final physical resolution — that is, if the module needs to appear 300px CSS wide on screen, you draw it from the start on an artboard that is 600px wide in real terms (or 900px for 3x), working directly "at the physical-pixel level". In this case the design is already retina-ready by construction, and the final export is done at 1x, with no multiplier at all: the file exported at 1x from the 600px artboard is already the full-resolution file to use in the email.

The key point is that the "2x" multiplier describes the ratio between the final file's resolution and the display size in CSS px, not an action that necessarily has to be carried out in the export panel. A file exported "at 1x" from a canvas built at full Retina resolution is just as retina-ready as a file exported "at 2x" from a 1x canvas with vector/high-resolution assets — provided that, in both cases, the final file genuinely contains double the real pixels relative to the size it will be declared at in HTML, and not just a larger canvas filled in by interpolation.

In practice, working directly at 2x from the start of the design eliminates the risk described in 4.1 at the root: since there's no doubling to carry out at export time, there's no way to "forget" and start from a low-resolution asset — every photo or image imported into the document must, from the very first moment, already have the pixels required to fill the artboard at full density.

05How to check whether an image is genuinely retina or just "inflated"

A quick test, with no special tools required:

  1. Open the file exported at 2x and zoom it to 100% (its true pixel size) on screen.
  2. Separately, open the original file (before export) and zoom it to 200% on screen.
  3. If the two images look equally blurry, the 2x export was a simple upscale: there was no real doubling of detail, only of the declared pixel count.
  4. If, instead, the 2x file looks sharper and richer in detail than the original zoomed to 200%, the source asset genuinely had enough visual information, and the export produced a genuinely retina-ready file.

06Practical checklist for retina-ready email

  • Start from high-resolution assets from the very beginning of the project: photos, screenshots and images imported into the design document should already have at least double (ideally triple) the pixels relative to the final size they'll be shown at in the email — you can't rely on export to "recover" resolution the source asset doesn't have.
  • Prefer vector elements wherever possible: logos, icons and CTA button text should stay vector-based (or, for text, be genuine HTML text — see the Table-based HTML guide, section 05) for as long as possible in the process, becoming raster only at the very last export step.
  • The final file must always have at least double (or triple) the real pixels relative to the final display size — whether that comes from exporting "at 2x" from a 1x design, or exporting "at 1x" from an artboard already built at full Retina resolution, the result is the same. Either way, the width/height declaration in HTML and CSS always stays at the 1x (logical) size.
  • Balance sharpness against file weight: doubling or tripling the resolution inevitably increases the file's weight. The image still needs to be well compressed (optimised JPEG for photos, compressed PNG for graphics with few colours) to stay within a reasonable weight — also bearing in mind Gmail's clipping threshold of roughly 102 KB for the whole email.
  • Always verify the final file on a real Retina device (or with the zoom test from section 05) before considering the asset finished, rather than trusting that the export dialog says "2x" in the file name.

07Further reading

A clear explanation of the same concept, aimed at the web in general (not just email), can be found in this article: "Retina Web Graphics Explained: 1x versus 2x, Low-Res versus Hi-Res".

The article's main points:

  • On the web, only the pixel dimensions of the file matter, not the "ppi" resolution set in software like Photoshop (e.g. 72ppi): the browser completely ignores that value and only looks at how many pixels the file has.
  • 1x (low-res): 1 CSS/HTML pixel maps to 1 physical screen pixel — matching the DPR=1 definition already covered in section 01.
  • 2x (hi-res / Retina): 1 CSS/HTML pixel maps to 2×2 physical screen pixels.
  • Practical example from the article: for an element that is 300px wide on the page, you prepare a 300px file for 1x screens and a 600px file for 2x screens. Both files occupy the same physical space on screen, but the 600px version looks sharper because it packs more pixels into the same area.
  • Historical context: the "Retina display" concept originated with Apple's iPhone 4, which doubled the screen's physical pixels (from 320 to 640 pixels horizontally) while keeping the same physical size as the iPhone 3 — the goal wasn't to show more content, but to render it more sharply.
  • The article recommends preparing both 1x and 2x versions for desktop (where many screens remain 1x), while for mobile a 2x version alone is generally enough, and suggests skipping 3x because, at the time it was written, the perceptible improvement didn't justify the extra file weight.

Context note: that last point (skipping 3x) reflected the state of the display market at the time the article was published. Today many recent smartphones (including several higher-end iPhones and Android devices) have 3x screens, which is why the checklist in section 06 of this guide still recommends evaluating a 3x export for email as well, when the file weight allows for it.
