Responsive Design

Reference guide · layout

"Responsive" in email doesn't mean one technique: media-query stacking, fluid (liquid) layout and hybrid coding solve the same problem in three different ways, each with its own trade-offs.

01Media-query stacking

Even while staying on the structural table base covered so far, you can still get responsive behaviour: the standard technique is to stack vertically, on small screens, the elements that sit side by side in columns on desktop.

1.1 How it works: media queries that stack the columns

Each module in the template (e.g. a two- or three-column block: image + text, or two products side by side) is built as a table whose cells carry a dedicated class. A media query in the head's <style> overrides that class below a certain screen width, forcing each cell to take up 100% of the width and behave as a block, so the columns end up one below the other instead of side by side:

HTML + CSS
<style>
  @media screen and (max-width: 600px) {
    .stack-col {
      display: block !important;
      width: 100% !important;
    }
  }
</style>

<table role="presentation" width="600" cellpadding="0" cellspacing="0" border="0">
  <tr>
    <td class="stack-col" width="300" valign="top">Column 1</td>
    <td class="stack-col" width="300" valign="top">Column 2</td>
  </tr>
</table>

In clients that don't support media queries (Outlook desktop, see the Table-based HTML guide), the rule is simply ignored: the two columns stay side by side as on desktop — a fallback that's still readable, the same controlled-degradation logic seen throughout this document.

1.2 Why stacking pays off on mobile

  • Text readability: two or three columns side by side on a ~375px-wide screen squeeze text into a column only a few dozen pixels wide, with constant line breaks and a font that looks smaller than intended. Stacked, each text block goes back to using the full available width.
  • Larger tap targets for buttons: a CTA button designed for a narrow column becomes small and hard to tap accurately. Stacked at full width, the button occupies a much larger tap area, reducing the risk of mis-taps.
  • No zooming or horizontal scrolling: a fixed-width multi-column layout that isn't stacked forces the recipient to pinch-zoom or scroll horizontally to read the content. Stacking the columns keeps everything readable with only vertical scrolling — the natural gesture on mobile.
  • A natural reading order: once stacked, the order in which elements stack (set by the order of the <td>s in the markup) matches a natural top-to-bottom reading order — the same pattern a mobile user follows scrolling with their thumb.
  • Degrades without breaking: because the technique relies on a media query that less permissive clients simply ignore, there's no risk of a broken layout in clients that don't support it: it just falls back to the side-by-side column layout, which still works (see Table-based HTML, section 03).

In practice: the base is always the table (see Table-based HTML, section 02), and the media query is the only extra layer needed to go from "columns side by side" to "columns stacked" below a given width — and this single change is often what has the biggest real impact on how readable an email actually is when read on a smartphone, which is where most opens happen today.

02Fluid (liquid) layout

The second approach doesn't stack anything and doesn't need a media query at all: instead of fixed pixel widths, every table and image is sized in percentages, so the whole layout naturally grows and shrinks with the available space.

HTML
<table role="presentation" width="100%" cellpadding="0" cellspacing="0" border="0"
       style="width:100%; max-width:600px;">
  <tr>
    <td>
      <img src="banner.jpg" width="600" alt=""
           style="width:100%; max-width:600px; height:auto; display:block;">
    </td>
  </tr>
</table>

width="100%" makes the table fill whatever space it's given; max-width stops it from stretching into an absurdly wide banner on a large desktop window. Because this is all plain inline attributes and inline CSS — no <style> block, no media query — it keeps working even in the clients that strip the <head> entirely, which is exactly where media-query stacking (section 01) falls back to its unstacked desktop layout instead.

The trade-off: fluid alone only resizes, it doesn't reorder. A two-column fluid layout stays side by side at every width — on a narrow phone screen the two columns just get proportionally thinner, which is exactly the "text squeezed into a sliver" problem described in 1.2. Fluid on its own is best kept for genuinely simple, single-column layouts — transactional emails, receipts, plain newsletters — not multi-column ones.

03Hybrid coding (fluid-hybrid)

Hybrid coding is the answer to the gap between the other two: it gets real column stacking, like media queries give you, but without needing a <style> block or media-query support at all — which means it survives being stripped down by aggressive webmail sanitisers or a forwarded/copy-pasted email, cases where an external or even a head <style> block (section 04 of the Table-based HTML guide) can simply vanish.

The trick: each "column" becomes its own block-level element sized with display:inline-block, width:100% and a pixel max-width. Placed side by side with no line break between them in the source, two such blocks sit next to each other while there's room, and wrap onto their own line the moment the container is narrower than both max-widths combined — a real reflow, driven by ordinary CSS box-wrapping, not a media query. Outlook (which ignores max-width and display:inline-block alike) is handed a separate, rigid, fixed-width table through an <!--[if mso]--> conditional comment, so it always gets the desktop side-by-side version — consistent with the rest of this document's Outlook-is-the-floor approach.

HTML
<div style="display:inline-block; width:100%; max-width:300px; vertical-align:top;">
  <!--[if mso]>
  <table role="presentation" width="300"><tr><td>
  <![endif]-->

  <table role="presentation" width="100%" cellpadding="0" cellspacing="0" border="0">
    <tr>
      <td style="padding:10px; font-family:Arial, sans-serif; font-size:14px;">
        Column content
      </td>
    </tr>
  </table>

  <!--[if mso]>
  </td></tr></table>
  <![endif]-->
</div><!--><div style="display:inline-block; width:100%; max-width:300px; vertical-align:top;">
  ... second column, identical structure ...
</div>

The </div><!--><div> join on one line is deliberate: any whitespace between two inline-block elements renders as a visible gap, so the two column tags have to butt up against each other in the source with no line break.

04Comparing the three approaches

ApproachNeeds <style>/media-query support?Reorders columns?Best for
Media-query stacking (section 01)Yes — degrades to the desktop layout where unsupportedYes, where supportedMost templates, when you can rely on a surviving <style> block
Fluid (section 02)NoNo — only resizesSimple, single-column, transactional emails
Hybrid (section 03)NoYes, alwaysMulti-column layouts that must stack even with <style> stripped

None of these is "the" correct answer — they're different trade-offs between how much control you get and how much markup complexity you take on. Many production templates mix them: a fluid single-column shell with one or two hybrid two-column modules dropped inside it where the layout genuinely needs to reorder.

05Summary

QuestionAnswer
What makes columns actually reorder on mobile?Either a media query (needs a surviving <style> block) or the hybrid inline-block/max-width trick (needs neither).
What's the simplest approach with the least markup?Fluid percentage widths — but it only resizes, it never reorders columns.
What survives a client stripping the <head>?Fluid and hybrid, since both rely only on inline attributes/CSS. Pure media-query stacking falls back to its unstacked desktop layout.
Practical rule

Reach for hybrid when a layout must reliably reorder regardless of client; plain media-query stacking is fine, and simpler to hand-write, everywhere else; keep pure fluid for the single-column templates that never needed to reorder in the first place.
