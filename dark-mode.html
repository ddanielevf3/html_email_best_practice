Dark Mode

Reference guide · rendering

In recent years, most email clients have introduced a dark mode, following the device's system setting. Here too the behaviour isn't uniform across clients, and on top of that — unlike the previous topics — the client can alter the email's appearance even without the developer writing a single line of dark-mode code, which introduces a new risk: automatic, unplanned rendering changes.

Two very different behaviours across clients

  • Clients that apply "smart" algorithmic inversion (typically some versions of Outlook mobile): they analyse the declared colours and invert or re-adapt them automatically for a dark background, with no precise developer control over the result. This can produce unwanted effects: a logo with a transparent background designed for a white background can become illegible, or dark text forced to light can end up with insufficient contrast against a background the client hasn't changed in the same way.
  • Clients that respect explicit developer declarations (Apple Mail, iOS Mail, and others): they let you declare, in a controlled way, how the email should behave in dark mode, via dedicated meta tags and CSS media queries.

New: Gmail can now block its own forced dark mode

Gmail used to be the textbook example of the first, uncontrollable category above: for years it applied a forced dark theme to every email with zero developer control — algorithmic darkening on Android (Chromium's engine), and a full luminance inversion on iOS, which had the perverse effect of turning emails that were already designed dark into light ones. That changed on 31 August 2026, when Google closed a 5-year-old bug report and shipped a fix, reported by email developer Mark Robbins on emailmarkup.org.

HTML
<meta name="color-scheme" content="light only">

With this tag in the <head>, the Gmail app (Android and iOS — the fix covers both, even though the bug was originally filed against Android only) skips its forced dark conversion entirely: the email renders exactly as designed, as if opened in light mode.

Three things worth knowing before reaching for this:
  • It's a block, not real dark-mode support: Gmail still doesn't support @media (prefers-color-scheme: dark) for custom dark styling, this only lets you opt out of its automatic conversion.
  • It only applies to Google accounts (@gmail.com and Google Workspace) opened in the Gmail app — not to third-party accounts (Yahoo, Outlook, etc.) that happen to be checked through the Gmail app.
  • light only can also stop your own @media (prefers-color-scheme: dark) styles from applying in other clients that respect the same meta tag, like Apple Mail desktop — see the fix right below.

The color-scheme meta tag mostly affects UI chrome (radio buttons, scroll bars), but some clients — Apple Mail on desktop among them — also use it to decide whether your own @media (prefers-color-scheme: dark) styles get applied at all. If you're setting light only for Gmail and shipping your own custom dark styles for other clients, reset the supported schemes back to both on :root:

CSS
:root {
  color-scheme: light dark;
}

This reset is only needed if you're also setting your own dark styles elsewhere in the email — if you're only using light only to block Gmail's forced conversion and nothing else, you can skip it.

Robbins' recommendation: don't add this as a blanket default to every template — recipients who enabled dark mode did so on purpose. It's most useful as an opt-in switch, and it's a particularly good fit for emails that were already designed dark, since it stops the iOS app's luminance inversion from flipping them to light against your intent.

How to declare explicit support

In the <head>, you declare support for both schemes:

HTML
<meta name="color-scheme" content="light dark">
<meta name="supported-color-schemes" content="light dark">

Then, in a <style> block (with the same support limitations already covered in the Table-based HTML guide — some clients ignore it regardless), CSS media queries are used to override background and text colours only when the device is in dark mode:

CSS
<style>
  @media (prefers-color-scheme: dark) {
    .email-bg   { background-color:#1a1a1a !important; }
    .email-text { color:#f0f0f0 !important; }
  }
</style>

These rules, being class- and media-query-based, can't be written inline (the same technical limitation covered for @font-face in the custom fonts section): they must go in the head's <style> block, knowing that clients that remove it will simply use the "light" version declared inline as the base.

Special attention to images

A logo or image with a transparent background, designed for a light background, can become illegible or "disappear" on a dark background (e.g. a black logo on a transparent background, invisible if the background behind it turns black). The most common fixes are: using logos with a light outline/structure that stays visible on both backgrounds, or showing two variants of the image (light and dark) and swapping between them via CSS based on prefers-color-scheme, in clients that support it.

Here too: verify with Litmus, don't assume

As with custom fonts, dark-mode behaviour isn't visible in your usual development environment: a desktop browser reproduces neither some clients' automatic inversion, nor the specific way Apple Mail or Outlook apply their own rules. The only reliable way to know how the email will really look is to use Litmus's dedicated dark-mode preview, which shows the actual rendering — a real screenshot, not a simulation — of the email in both light and dark mode across the main clients, letting you spot disappearing logos, insufficient-contrast text or unwanted colour inversions in advance, before sending, instead of finding out from recipient complaints.
